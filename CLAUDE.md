## What this is

A static-data Next.js 16 App Router demo of an Indian EV marketplace, styled to match a supplied "EV Motion" design template. It has been through **seven** major work sessions on top of the original build: a full production-readiness QA cycle (audit → Critical → High → Medium → Low fixes, all resolved — see `FINAL_QA_REPORT.md`), a session that replaced every visual-only interaction with real logic and generalized the codebase into a multi-category architecture including **commercial EVs** as a third category, a **production polish pass** (see `PRODUCTION_POLISH_REPORT.md`) that re-audited the whole site end-to-end and fixed a page-wide layout bug plus a root-cause search-navigation bug, a Compare page premium rebuild + polish pass, a site-wide centralized pricing pass, and — most recently — a **homepage redesign** (2026-08-15, see `HANDOFF.md`'s "Homepage Redesign — Premium Direction") that restructured Hero/Search/Trending/Key Highlights, replaced the flat Sponsored banner with a premium Featured Banner, and rebuilt the listing/upcoming cards and right sidebar. **This paragraph's "no backend" framing is out of date and kept only for history — see points 24-26.** Vehicle data is still static TypeScript, but Supabase really does back lead capture and analytics (since 2026-08-16), and ImageKit really does deliver AI-generated vehicle-type illustrations (since 2026-08-17). What is still true: no auth, no user accounts, no CMS, reviews are local React state, and **no vehicle has a real photograph** — `photoUrl` is empty for all 123.

**Important right now:** the project is mid-expansion from its original 36-vehicle demo into full India-market coverage, one small OEM batch at a time (see `HANDOFF.md`'s "Full-Market Expansion — Batch Log"). **Batches 1-4 are done** — `src/lib/data/cars.ts` has 54 records across 15 car OEMs (Tata, Mahindra, MG, Hyundai, Kia, BYD, BMW, Mercedes-Benz, Audi, Volvo, MINI, Porsche, Lotus, Rolls-Royce, VinFast); `src/lib/data/two-wheelers.ts` has 69 records (55 scooters + 14 motorcycles) across 31 two-wheeler OEMs. Commercial EVs (Batch 5) is not started — **do not start a new batch without being asked**, each batch stops for approval when done. Separately, the commercial-category *architecture* is complete and working; the commercial *data* is not — `src/lib/data/commercial.ts` is an empty array. `src/lib/data/_research-commercial.ts` (earmarked for Batch 5) still contains real, researched-but-unmerged data. `src/lib/data/_research-two-wheelers.ts` no longer exists. **No vehicle has real photo data yet** — the production polish pass removed every externally-sourced/locally-cached photo to eliminate copyright risk, and nothing has been populated through the ImageKit plumbing since; don't add a raw external image URL back for any Batch 5 records. Cards now render a generic AI body-type illustration where one exists, falling back to the branded placeholder — **neither is a photo of the vehicle, and neither belongs in `photoUrl`** (point 26). **A separate, parallel `Vehicle.specs` field** (dimensions/safety/warranty/features/motor/tyres/suspension/brakes — added for the Compare page rebuild) is populated for **65 of 123** vehicles as of 2026-08-20 (Batch 6 pilot + Batch 7 sub-batches 1-2, see `HANDOFF.md`) — every other vehicle has it fully `undefined` and every UI reading it must render "Not officially specified" rather than guess; never backfill it with a formula or estimate. **Extending this coverage is the live task; work brand-by-brand rather than scattered, and see point 28 for the three traps that keep recurring.** **`toVehicleDetail.ts` used to do exactly that and no longer does — see point 22 below.** See `HANDOFF.md`'s "Known Limitations" and "How the next Claude session should continue" before doing anything with the vehicle database.

## Before you touch anything

1. **Check `git status` and `git log` first.** Three sessions' worth of work (location/filters/search, the commercial-category architecture, and the production polish pass) have a history of sitting uncommitted at once on top of the original QA-cycle commits — don't assume anything in this repo's current file state is saved unless you verify.
2. **`VehicleCategory` is `"car" | "2-wheeler" | "commercial"`, driven by a registry (`src/lib/data/categories.ts`), not a hardcoded binary.** If you're about to write `category === "car" ? X : Y` anywhere, stop — check whether `routeSegmentFor()`, `categoryConfig()`, or `filterConfigFor()` already covers it. That exact ternary existed in 7+ files before the category-generalization pass; don't reintroduce it.
3. **This shadcn setup uses Base UI, not Radix.** Composing a non-Button element into `Button`/`SheetTrigger`/`DialogTrigger`/etc. needs the **`render` prop**, not `asChild`: `<Button render={<Link href="/cars" />} nativeButton={false}>`.
4. **Next.js 16 has real breaking changes** vs. training-data assumptions (see `AGENTS.md` above and `node_modules/next/dist/docs/`). `params`/`searchParams` are `Promise`s; `PageProps<'/route/path'>` is a generated global type. **A brand-new route's `PageProps` type won't exist until you run `next build` or `next dev` once** to regenerate `.next/types` — a bare `tsc --noEmit` on a just-added route will falsely error until then.
5. **Grep before editing shared files.** `search.ts`, `vehicle-labels.ts`, `listing-params.ts`, `vehicle-filter-options.ts`, `structured-data.ts`, `categories.ts`, `state-charges.ts`, `utils.ts`, `VehicleImage.tsx`, `PlaceholderImage.tsx`, `LeadCaptureDialog.tsx`, `VehicleSearchBox.tsx`, `BrandLogo.tsx`, `LocationContext.tsx`, `ResponsivePopover.tsx` are each used in multiple places on purpose.
5a. **When adding vehicles in a data-expansion batch, re-check `vehicle-filter-options.ts`'s `priceBounds`/`rangeBounds`/`batteryBounds`** against the new dataset's min/max before calling the batch done. Batch 1 hit this live: a new car's price and battery capacity exceeded the old bounds and silently vanished from `/cars` and the homepage filter chips despite a clean `tsc`/`eslint`/`build` — neither catches numeric filter-bound drift, only live verification of the listing count does.
6. **`loading.tsx` hangs routes in this app — root *or* segment-scoped. Don't add one.** The original QA pass found this for a root `src/app/loading.tsx`. Re-tested properly on 2026-08-16 with segment-scoped files (`cars/`, `two-wheelers/`, `commercial/`, `compare/`) on the assumption that only the root was affected: **they hang too.** `/cars` sat on its skeleton forever, with the real listing streamed into the DOM but never swapped in — reproduced in `next dev` *and* in a `next start` production build, and still reproduced with `src/app/template.tsx` removed, so it is neither a dev-only quirk nor the `PageTransition` template. Root cause is unresolved (something in this app's tree never settles the Suspense boundary); the files were removed rather than shipped. Scoped **`error.tsx` is fine** and is in place for all five segments — that was verified live by throwing from a page and confirming the boundary caught it with the navbar/footer shell intact. If you want streaming fallbacks later, treat it as a real investigation with a production build in the loop, not a quick add.
7. **Never hand-roll `₹` lakh/crore formatting.** Call `formatPriceLakh`/`formatPriceRangeLakh` from `src/lib/utils.ts` instead of a new inline `` `₹${x.toFixed(2)}L` `` template — the production polish pass consolidated 4 separate copies of this into one shared helper specifically to prevent drift.
8. **Any CSS Grid container with a `.scroll-row` (horizontal-scroll) descendant needs `minmax(0, 1fr)` on its fractional track, not a bare `1fr`.** A bare `1fr` track's implicit min-width is its max-content size, so a horizontal-scroll child's full unscrolled width can silently stretch the whole grid (and page) past the viewport — this caused a real page-wide overflow bug in `MainLayout.tsx`, found and fixed in the production polish pass. Check this first if adding a new horizontal-scroll section inside any grid.
9. **No vehicle has a `photoUrl` any more, and none should.** The production polish pass removed every externally-sourced and locally-cached vehicle photo to eliminate copyright/provenance risk. Don't reintroduce external image URLs when adding vehicles (e.g. in Batch 5) — `VehicleImage.tsx`'s branded-placeholder fallback is the only rendering path now, by design.
10. **If adding/editing curated search terms** (popular searches, etc.), verify they resolve via `searchVehicles()` first — the substring matcher can silently fail on a multi-word "OEM full name + model" query if the brand's real name isn't a single word (e.g. "Tata Motors", "Ola Electric"). Bare model names are always safe.
11. **Quality gate, every time:** `npm test`, `npx tsc --noEmit`, `npx eslint .`, `npm run build` — all four are clean as of this handoff (**265 tests**, 416 routes). Keep them clean.
11a. **The test suite (Vitest, `npm test` / `npm run test:watch`) covers pure logic only — no jsdom, no React Testing Library, by design.** Tests live beside their subject as `*.test.ts`. What's covered and why: the site-wide pricing system (`vehicle-pricing/pricing.test.ts` — EMI amortization, on-road breakdown summing exactly to its parts, per-city adjustments across all 157 cities), the Compare winner engine (`compare/winnerEngine.test.ts` — above all the >=2-known-values rule from point 15), compare-slug build/parse round-tripping (`compare/slug.test.ts` — a mismatch would make pre-rendered pages 404), search (`search.test.ts` — tokenization, typo tolerance, category gating, and that every curated popular term still resolves per point 10), the data-honesty invariant (`data/ev-motion/toVehicleDetail.test.ts` — asserts no spec is ever derived, per point 22), and filter-bound drift (`vehicle-filter-options.test.ts` — the exact silent failure described in point 5a), plus the four suites added with the 2026-08-21 data-model decisions:
    **`vehicle-torque.test.ts`** (the hub-vs-shaft comparability rule and that the real catalogue crowns no cross-convention Torque winner),
    **`vehicle-safety.test.ts`** (the six-year NCAP expiry window, and that no lapsed rating renders without saying so),
    **`vehicle-availability.test.ts`** (that a `discontinued` record is gone from every buyable surface and still served on its own),
    and **`imagekit.test.ts`** (the configured/unconfigured flag every ImageKit render path branches on),
    plus **`vehicle-battery.test.ts`** (2026-08-21 — the gross-vs-usable gate, that the real catalogue crowns no cross-convention Battery
    winner, and that no battery figure moved when the field was added).
    - These were **mutation-checked**: reintroducing the `batteryKwh * 2.3` power formula, relaxing the winner threshold to 1, and narrowing a price bound each make the suite fail, naming the offending vehicle. The 2026-08-21 suites were checked the same way — defaulting two-wheeler torque to `"shaft"`, un-annotating the iQube's 140 Nm, making NCAP results never expire, reading `ncapRating` instead of `currentNcapRating`, un-discontinuing a Bajaj record, putting the full catalogue back in the search index, and treating an empty ImageKit endpoint as configured each fail 1-8 tests. If you change one of these modules and the suite still passes, be suspicious.
    - UI behaviour stays browser-verified (point 12). That is deliberate — the bugs this project has actually hit (RSC serializability, grid overflow, a stuck Suspense boundary) are ones jsdom would not have caught.
12. **Verify UI/responsive changes live in a browser**, at multiple widths — including the *exact* pixel width you suspect might be tight, not just round breakpoints, and including the *default* state as well as any worst-case content (a page-wide grid-overflow bug was present at the default city, not only with a long one). If screenshot tooling isn't available, compare `document.documentElement.scrollWidth` vs `clientWidth`. Note: this environment's synthetic "Enter" keypress reports `e.key === "Unidentified"`, not `"Enter"` — verify keyboard-nav-dependent behavior via an equivalent click instead of assuming a failed Enter-key test means the app is broken. **Second, worse instrument trap, hit on 2026-08-21 against Production:** when the browser pane is not actually displayed it does not composite, so **`requestAnimationFrame` never fires**. Framer-motion's enter animation is rAF-driven, so `PageTransition`'s wrapper (`main > div`) stays at its initial `opacity: 0; translateY(8px)` on **every** page, and `document.documentElement.scrollWidth` reads larger than `clientWidth` on pages that are actually fine. Both look exactly like real bugs — an invisible page and a page-wide overflow. **Before believing either, check `requestAnimationFrame` actually fires, and for overflow check whether the page can really pan (`window.scrollTo(9999,0)`; if `scrollX` stays 0 there is no user-visible overflow).** The scrollWidth-vs-clientWidth heuristic above is still the right first check — it just needs the can-it-actually-scroll follow-up before you act on it.
13. **Background research agents can fail on session usage limits.** This happened in a prior session — all 3 parallel data-research agents failed simultaneously, though 2 had already written usable output before failing. Check for partial output files before assuming nothing was produced.
14. **This repo's `CommandDialog` (`src/components/ui/command.tsx`) only provides the Dialog shell — it does NOT wrap its children in cmdk's `<Command>` store provider**, unlike the upstream shadcn convention some training data assumes. Putting `CommandInput`/`CommandList`/`CommandItem` directly inside `<CommandDialog>` without an explicit `<Command>` wrapper crashes at runtime with `TypeError: Cannot read properties of undefined (reading 'subscribe')` — a real bug hit and fixed while building `ChangeVehicleModal.tsx` during the Compare page rebuild. Always compose `<CommandDialog><Command><CommandInput/>...</Command></CommandDialog>` explicitly.
15. **The Compare page's winner engine (`src/lib/compare/winnerEngine.ts`) requires at least 2 known values among the compared vehicles to declare a "winner"** for any metric — a single known value with the rest `null`/unresearched does NOT auto-win (there's nothing real for it to have beaten). Found live: with only 15/122 vehicles carrying real `specs` data, a metric known for exactly one of 3 compared vehicles was originally rendering a false "winner" crown. Don't relax this threshold back to 1 without re-introducing that bug.
16. **There is exactly one pricing system for the whole site — `src/lib/vehicle-pricing/`, via the `useVehiclePricing(vehicle)` hook (`src/hooks/`) — never add a second one.** An earlier same-day pass deliberately split VDP pricing from a legacy `src/lib/pricing.ts` used by Compare/homepage; that split was undone and `pricing.ts` deleted once the brief expanded to "every price on the site must be city-aware, single source of truth." Ex-showroom price itself is city-adjusted (not just the on-road extras) via `cityPriceZones.ts`'s formula-driven model — a per-state "logistics zone" % plus a small non-metro tier extra, deliberately a formula rather than a ~19,000-row (157 cities × 122 vehicles) hand-typed table that would look precise while being pure invention. If you're computing a price or EMI anywhere, it should be `useVehiclePricing`/`getVehiclePricingSnapshot`, never a new inline formula.
    - **`vehiclePricingSubject()` (the raw-`Vehicle`-to-hook-input adapter) deliberately lives in `src/lib/vehicle-pricing/subject.ts`, not in `useVehiclePricing.ts` itself** — `useVehiclePricing.ts` is `"use client"`, and a "use client" file's exports can't be *called* as plain functions from a Server Component (only rendered/passed as a Client Component), even if the export itself has no hooks. Hit this exact error at build time: `next build` failed with "Attempted to call vehiclePricingSubject() from the server but vehiclePricingSubject is on the client" when it briefly lived in the hook file and `ListingCard`/`RankedListCard`/`CompareCard` (Server Components) tried to call it directly. Any future plain helper that Server Components need to *call* (not just components they render) must live in a non-"use client" module.
    - **`src/components/pricing/VehiclePriceText.tsx`/`VehicleEmiText.tsx`** are the pattern for rendering a live price inside a Server Component card: a tiny client leaf taking plain serializable props (`{id, name, priceRangeLakh}` — no functions), safe to embed directly. Reuse this pattern for any new pricing widget rather than converting the whole parent card to `"use client"`.
17. **`src/components/compare/SpecTable.tsx` must stay a Server Component — do not add `"use client"` to it.** Every section (`DimensionsSection.tsx`, `SafetySection.tsx`, etc.) is itself a Server Component that imports a `SPEC_ROWS` array from `metrics.ts` and passes it straight into `<SpecTable rows={...}>` — and each `SpecRow` carries `render`/`barValue` **functions**. Next.js's RSC boundary throws `Functions cannot be passed directly to Client Components` the instant a function-bearing prop crosses into a `"use client"` component. This was a real bug hit and fixed during the premium polish pass (SpecTable briefly needed `useState` for the "show unavailable specifications" toggle, got `"use client"` added, and broke every SpecTable-based section at runtime — caught live, not by `tsc`/`eslint`/`build`, none of which type-check RSC serializability). The fix, and the pattern to keep: the toggle's interactive state lives in its own tiny client child, `UnavailableRowsToggle.tsx`, which receives the already-rendered collapsed rows as `children` (a JSX tree, not a function — safe to cross the boundary) rather than receiving `SpecRow[]` itself. Any future interactive addition to SpecTable should follow the same shape: isolate the `"use client"` boundary to a leaf component that takes pre-rendered JSX as children, never one that receives the row/column data objects directly.
18. **Read `HANDOFF.md`'s "Design System — Locked Decisions" before changing the homepage layout, the color theme, or `/compare`'s design.** These are explicit, user-confirmed "don't revert" decisions, not just current defaults.
19. **`ListingGrid.tsx` and `UpcomingSection.tsx` are single-row horizontal-scroll at every width, not just on mobile** (changed 2026-08-15, intentional) — don't revert to a wrapping `sm:grid-cols-*` layout.
20. **If a sticky sidebar's height doesn't naturally match the column beside it, measure the gap at runtime (see `StickyClearanceSpacer.tsx`), don't hardcode a padding/margin guess.** A hardcoded `lg:pt-40` was tried for exactly this in the 2026-08-15 homepage pass and broke (the real gap depends on content length and viewport width).
21. **~~ImageKit infra exists but is unpopulated; Supabase config exists but isn't integrated.~~ Both are live now — for different things, and neither means "the vehicles have photos."** Supabase backs lead capture and analytics (points 24-25). ImageKit delivers the AI-generated vehicle-type illustrations (point 26). **`Vehicle.images.photoUrl` is still empty for all 123 vehicles and real photography is still unsourced** — that is the claim that matters, and it has not changed.
26. **AI-generated imagery is placeholder art keyed to body type. It must never depict a specific model, never be photorealistic, and never populate `photoUrl`.** `src/lib/vehicle-illustrations.ts` is the registry and its header is the full argument; `scripts/generate-vehicle-illustrations.mts` regenerates assets; `vehicle-illustrations.test.ts` (16 tests) enforces the rules and is mutation-checked.
    - **Why per body type, not per model:** every SUV shares one drawing, so it reads as category art the way the SVG icon it replaced did. Keying art to a model would make the site assert what that specific vehicle looks like — a fabrication in the sense of point 22.
    - **Why never photoreal:** the first probe returned a near-copy of a specific real production SUV's design, because that is the training data. The style string's `not photorealistic` / `no logos` / `no badges` / `no brand marks` / `no number plate` clauses are load-bearing; the tests fail if you remove one, and separately scan every subject prompt for real OEM and model names.
    - Assets are generated once and **uploaded to a stable library path**, never served off the `ik-genimg` generation URL — that would embed the prompt in every page's HTML and re-run a paid, non-deterministic generation on any cache purge.
    - A body type with no illustration falls back to the SVG icon, so the registry can be filled in incrementally. **Never declare a `path` before the asset exists** — that renders a broken image. `2-wheeler:scooter` is currently commented out for exactly this reason.
    - **The same rule now covers a missing `NEXT_PUBLIC_IMAGEKIT_URL_ENDPOINT`, via `IMAGEKIT_CONFIGURED` in `src/lib/imagekit.ts`.** `@imagekit/next` does *not* fail loudly without an endpoint — `<Image>` and `buildSrc` still emit a src, just one with no host in front of the path — so an unset variable renders **broken images, not nothing**. That happened: it was unset in Vercel until 2026-08-20 and silently broke every illustration in Production. All four render paths now check the flag first and fall back (`PlaceholderImage` → SVG icon, `VehicleImage` → branded placeholder, `VehicleGallery` → "coming soon" slots, `structured-data.ts` → no `image` property). **Any new ImageKit-delivered asset must branch on it too.**
27. **`scripts/*.mts` run directly under Node's native type stripping**, which requires the explicit `.ts` extension on relative imports — hence `allowImportingTsExtensions: true` in `tsconfig.json` (safe: `noEmit` is on). Keep the `.mts` extension so Node doesn't warn about the package's CommonJS default.
28. **Three spec-research traps that have each bitten this project more than once.** (a) An NCAP rating quoted beside an EV is often its **petrol twin's** — caught on Tiago EV, Punch EV, Sierra EV, Carens Clavis EV, Syros EV (whose famous 5-star Bharat NCAP result is the petrol Syros's) and — as a *recorded* error rather than a near-miss — Kona Electric, whose 5-star result had been credited to Euro NCAP when Euro NCAP has never tested the EV (ANCAP has); if an ICE version exists, assume the rating is the twin's until proven otherwise. **And the trap is wider than ICE-vs-EV: the real question is "was THIS structure tested, and is the result still current".** Four shapes seen so far: (i) ICE twin; (ii) a different bodyshell of the same EV; (iii) a legitimate Euro-NCAP extension that has since EXPIRED (results lapse after 6 years — G 580, EX40, Q8 e-tron; **since 2026-08-21 `ncapYear` records the age and these three are recorded again rather than omitted, rendered as expired — see point 29. Shape (iii) is now a presentation concern, not a reason to drop data; shapes (i), (ii) and (iv) still are**); (iv) a platform sibling from a DIFFERENT MANUFACTURER (Audi e-tron GT quoting the Porsche Taycan). Counter-cases where the check must NOT fire: MG ZS EV and Volvo EC40 were both tested directly. The iX1 LWB sold in India has a 2800mm wheelbase against the 2692mm standard-wheelbase iX1 Euro NCAP crashed, so that 5-star result is omitted even though it is genuinely an EV result. Contrast the i5, where the tested eDrive40 and India-market M60 share one G60 shell and the rating is recorded. Bodyshell, not badge. Born-electric models with no ICE twin (BE 6, XEV 9e, Ioniq 6/9, EV9) are safe. **The trap runs both ways, so check rather than assume in either direction:** MG ZS EV really was tested by Euro NCAP at 5 stars while the petrol ZS scored 3, so its rating is correct and must not be "corrected" away. (b) A published **width** may include mirrors; this dataset records body width, and mixing conventions crowns false winners in Compare. (b2) **Two-wheeler torque comes in two incompatible conventions**: hub-motor scooters (TVS iQube) quote torque at the WHEEL, mid-drive scooters (Ather, Ola, Bajaj's belt-driven Chetak) quote it at the motor SHAFT before belt multiplication. 140 Nm vs 26 Nm is a definition, not a difference — never put both in one Compare row. See sub-batch 7. **The schema can now say which is which (`torqueMeasuredAt`, 2026-08-21) and the comparison is refused automatically — see point 29.** The trap is NOT retired, it moved: it is now a *recording* discipline. **Establish the measurement point from the source before recording a two-wheeler torque figure**, because an unannotated one is treated as unknown and silently drops out of ranking. `ampere-nexus`'s 35 Nm is in exactly that state on purpose — no source states where it was measured, and "Ampere is a hub-motor brand" is a generalisation, not a measurement. (c) A figure that **reconciles across units** is trustworthy (110 kW = 147.51 bhp = 149.55 PS); one that doesn't is a guess wearing precision — omit it. A 3 kW rounding artifact on the BE 6 was enough to hand it a false Power crown over the XEV 9e it shares a motor with. **This applies to an OEM contradicting ITSELF, not just to aggregators disagreeing:** chetak.com states a 5yr/70,000km warranty in its spec block and 3yr/50,000km in the FAQ on the same page, so Bajaj warranty is recorded nowhere. OEM-primary is a strong signal, not an infallible one — still reconcile.
29. **Four schema fields exist because a number can be real and still not mean what the row beside it means. Read this before adding a comparison metric.** Resolved 2026-08-21; each replaced an owner decision HANDOFF.md had held open, and each has one lib module that owns the policy — put new rules there, not in a component.
    - **`VehicleMotor.torqueMeasuredAt: "shaft" | "wheel"`** (`src/lib/vehicle-torque.ts`). Hub-motor scooters publish torque at the wheel, mid-drive scooters at the motor shaft. TVS's 140 Nm beside Ather's 26 Nm is a definition, not a fivefold difference. **Nothing converts between them** — no OEM here publishes a reduction ratio, so a conversion would be invention (#22). **Cars default to `"shaft"`; two-wheelers deliberately have NO default**, so an unannotated two-wheeler figure is *unknown* and drops out of ranking rather than being assumed comparable. Giving two-wheelers a default silently re-admits the exact bug this fixes — a test pins that.
    - **`VehicleSafety.ncapYear`** (`src/lib/vehicle-safety.ts`). Euro NCAP and ANCAP results lapse six years after publication; Bharat NCAP and Global NCAP publish no window, so theirs don't expire rather than having one guessed. **Read ratings through `ncapResultFor()`/`currentNcapRating()`, never off `ncapRating` directly** — the latter cannot tell a live rating from a 2019 one. A lapsed result stays visible with an explicit "rating expired" and is excluded from the winner engine, the safety score and the homepage banner's stars. This also let three ratings previously dropped *entirely* for age be restored (G 580, EX40, Q8 e-tron); ratings that failed on **attribution** stay absent, so don't read `ncapYear` as licence to restore the e-tron GT's borrowed Taycan stars.
    - **`LaunchStatus: "discontinued"`** (`src/lib/vehicle-availability.ts` — read its header for the exact surface-by-surface split). Excluded from listings, brand pages, homepage rails, related/similar, the pre-rendered comparison set and the compare picker; still served on its own detail page, in comparisons naming it, in the sitemap, and in structured data as `schema.org/Discontinued`. **It is deliberately not a fourth availability filter chip.** `getAllVehicles()`/`getVehiclesByCategory()` stay unfiltered on purpose (static params, sitemap, slug lookup, the honesty tests); discovery surfaces call `getCurrentVehicles()`/`getCurrentVehiclesByCategory()`.
    - **`Vehicle.batteryMeasuredAt: "gross" | "usable"`** (`src/lib/vehicle-battery.ts`). A published kWh figure is either the whole installed pack or what survives the manufacturer's buffer, and this catalogue holds both. **`bmw-ix` records 105.2 (usable, from a 111.5 kWh pack) while `bmw-i4` beside it records 83.9 (gross) — BMW uses both conventions inside one line-up, and so does BYD.** Ranking them directly docks the iX 6.3 kWh on a definition. **There is deliberately NO category default** — the difference from `torqueMeasuredAt`, which can default a car to `"shaft"` because no hub-motor car exists. No category is unambiguous here, so an unstamped vehicle is *unknown* and drops out of ranking. **Neither a gross-everywhere nor a usable-everywhere rewrite is reachable**: Mercedes-Benz publishes usable capacity and never a gross figure, while Tata/MG/Mahindra/VinFast and every two-wheeler OEM publish one nominal figure and never a usable one — so standardising either way means recording an estimate as a specification (#22). **All 54 cars carry a basis (43 gross, 11 usable, 0 unresolved)** as of 2026-08-22; **all 69 two-wheelers are deliberately unstamped**, which is why no two-wheeler comparison shows a Battery winner. **BYD was the hard case and is worth knowing about: BYD's own spec sheet labels the row only "Battery capacity (kWh)"**, so OEM-primary could not settle it — the Atto 3's documented 60.48-usable-of-64.8-total pair, EV Database estimating rather than citing a gross, and a WLTP reconciliation at a consistent ~87% across three Seal variants did. Full per-record classification and sourcing: `BATTERY_CONVENTION_SURVEY.md`.
    - **Search is on the KEEP side of that split, and the line it draws is worth copying.** A discontinued vehicle stays in `/search-index.json` and stays findable by name — typing a name is *asking for a specific thing*, and someone who owns one must be able to reach its page. It just must not pass as current stock, so `VehicleIndexEntry.discontinued` flags it and `VehicleSearchBox` renders a "Discontinued" chip on the result. Curated **popular-search chips are the opposite case** — those are the site recommending a query, so they point only at current vehicles (`popular-searches.ts`). **Findable-and-labelled, not hidden**; hiding it would have been a worse answer to the same question, the way omitting an expired NCAP rating was.
    - **`WinnerMetric.comparable` / `SpecRow.comparable`** are the general mechanism the first of these needed: a **set-level** gate, because `value()` sees one vehicle at a time and cannot tell that two real numbers describe different quantities. A gated metric goes `insufficient-data`, leaves the Winner Ribbon tally alone, and **loses its proportional bar** — a bar is a ranking too. **Width-with-mirrors (#28(b)) is the obvious next candidate for it.**
22. **The whole site follows one data-honesty rule: a specification is either real sourced data or it renders as "Not specified" — never a formula.** This was made a hard invariant on 2026-08-16; before that, `toVehicleDetail.ts` derived and displayed as fact: power (`batteryKwh × 2.3`), torque (`power × 2.0`), DC fast-charge time (`acHours × 60 × 0.4`), battery chemistry ("NMC" for every non-BYD vehicle), boot space (a per-body-type lookup, so every SUV claimed 400 L), drive layout (guessed from whether a variant name contained "AWD"), connector type, and a flat 8yr/160,000 km warranty for every car. A "Price History" ownership tool also reported `currentPrice × 1.012` as the price three months ago. All of these are gone. When adding a VDP field:
    - Source it from `Vehicle.specs` (or a first-class `Vehicle` field) and type it optional, or don't add it.
    - Render absence through `src/components/common/UnavailableValue.tsx` — the same component the Compare page uses. It was promoted out of `components/compare/` so both pages share one treatment.
    - **This is not only a VDP concern: `src/lib/compare/` reads `VehicleDetail`, so the Compare page was consuming the fabricated values too.** `metrics.ts` fed derived power/torque into `barValue`, which meant battery capacity was counted three separate times in the winner engine and Power was effectively a restatement of Battery; `quickVerdict.ts`'s "Best Family EV" ranked table-lookup boot space; `faqs.ts` published a derived fast-charge time into schema.org `FAQPage` markup. If you reintroduce a derived value anywhere in `toVehicleDetail.ts`, you are silently changing comparison verdicts and structured data, not just one page's copy.
    - The two surviving computed blocks are **calculators, not specs**, and each states its assumptions inline: running/charging cost (₹/unit, km/day, fuel efficiency) and `realWorldRange` (which now carries its derating `factors` so the UI prints "Est. 80% of claim" rather than implying a measurement). Keep that property if you touch them.
23. **Never import `@/lib/data` (or anything that transitively reaches it) from a `"use client"` component.** The barrel's module body builds a category→vehicles map, so importing *any* export from it — even just `getOemBySlug` — pulls all 122 full vehicle records into that route's client bundle. This was costing ~110-130 KB of JavaScript on every page, because `Navbar` sits in the root layout and reached `getAllVehicles()` through `VehicleSearchBox` → `@/lib/search`. Rules:
    - Client components needing brand metadata import **`@/lib/data/oems`** directly (it carries no vehicle data). Same for `@/lib/data/categories`, `@/lib/vehicle-filter-options`, `@/lib/compare/slug`.
    - **`@/lib/search`, `@/lib/compare/slug` and `@/types/search-index` are deliberately data-free — keep them that way.** Their server-side counterparts are `@/lib/search-index.ts` (builds the index) and `@/lib/compare/parse-slug.ts` (resolves a compare slug back to vehicles); those two, plus `@/lib/filter-facets.ts` and `@/lib/featured-vehicle.ts`, must only ever be called from Server Components.
    - Search runs against a **lazily fetched index** (`/search-index.json`, ~22 KB, built by `buildSearchIndex()`, fetched on first focus and memoized by `@/lib/search-index-client`), not the catalog. `VehicleIndexEntry` carries only what a result needs to be matched, linked and thumbnailed.
    - When a client component needs real vehicle records, **hoist the lookup into its Server Component parent and pass the result as a prop** — the pattern used by `FeaturedBanner` (`featured`), `SearchCard` (`seatOptionsByCategory`) and `SectionCompareSimilar` (`similar`).
    - **`/compare` and `/compare/[slug]` are the one accepted exception**: `CompareHero` holds `Vehicle[]` in client state and calls `toVehicleDetail()` there, `ChangeVehicleModal` is a picker over the whole category, and `ComparisonEndingSection` resolves arbitrary localStorage slugs into renderable cards. Removing the catalog from those needs a real refactor (server actions or an extended index), not an import tweak.
    - To check for a regression, trace client components' transitive imports for a path into `src/lib/data/{index,cars,two-wheelers}.ts`, or grep the built chunks: `grep -o 'slug:"[a-z0-9-]*"' .next/static/chunks/*.js | sort -u | wc -l` should not report ~122 distinct slugs for any chunk outside the compare route.
24. **Lead capture (`src/lib/leads/`, `POST /api/leads`) is the site's only untrusted-input-to-database path, and it handles personal data.** Every CTA (`LeadCaptureDialog`) posts here; the route rate-limits, then checks the honeypot, then validates, then stores — in that order, and nothing reaches the database before validation.
    - **Two key modes, and they need different database setups** — `supabaseConfig()` reports which is active. A **secret** key (`sb_secret_…` / legacy `service_role`, via `SUPABASE_SECRET_KEY` or `SUPABASE_SERVICE_ROLE_KEY`) bypasses RLS, so `0001_leads.sql` alone is correct and `/api/leads` is the only path that can write a lead — **this is the preferred setup**. A **publishable** key (`sb_publishable_…` / legacy `anon`) is subject to RLS and additionally needs `0002_leads_publishable_key_policy.sql`; the cost is that anyone holding that public key can POST rows straight to PostgREST, skipping this route's validation, honeypot and rate limiting, leaving only the table's CHECK constraints. A secret key wins if both are set.
    - **A secret key is server-side only** — never `NEXT_PUBLIC_`, never imported from a `"use client"` file. `supabaseLeadStore.ts` is the only module that reads it, and only `leadStore.ts` imports that.
    - **`public.leads` has RLS enabled with zero policies** in `0001`, which denies anon and authenticated outright. Don't add a permissive read policy to "make it work" from the browser — that would expose every submitter's name, phone and email. `0002` grants INSERT only (no SELECT/UPDATE/DELETE), i.e. a write-only drop box.
    - **Validation lives in `leads/validation.ts` and is shared with the dialog, but the server copy is the actual gate** — anyone can POST directly. It is allow-list based: unknown `fields` keys are dropped rather than passed through, so a caller can't push arbitrary columns at the table.
    - **Never log a lead object.** It contains PII; the route logs only the store's error message, which is PII-free by construction.
    - **When the env vars are absent the endpoint returns `not-configured`, and the dialog says so rather than showing a confirmation.** That is deliberate and matches this project's honesty convention (point 22) — do not "simplify" it by treating unconfigured as success. Someone handing over their phone number is owed an accurate answer.
    - **The rate limiter is in-memory and therefore per-instance**, not global: it raises the cost of casual form-spamming and resets on redeploy or across multiple instances. `rateLimit.ts` documents the upgrade path (shared store) — it is not pretending to be a flood defence today.
25. **Analytics (`src/lib/analytics/`, `POST /api/events`) is first-party, cookie-less, and deliberately carries no personal data.** Four properties hold it together, and breaking any of them is a privacy-policy decision rather than a code change: **no cookies and no durable identifier** (the session id lives in `sessionStorage`, dies with the tab, and can't recognise a returning visitor or follow anyone across sites — which is also why the site needs no analytics consent banner); **no IP is ever stored** (the route uses it for rate limiting and discards it); **no PII in payloads** (a `lead_submitted` event records the CTA and vehicle, never the name/phone/email — those live only in `public.leads`); and **`analytics_events` is RLS-deny-all**, same as `leads`.
    - **`track()` must never throw and never block.** Every entry point is wrapped and swallows its own errors, and events are queued then flushed on a timer or at page-hide via `sendBeacon`. Analytics is never worth degrading the product for — if you add a call site, keep it fire-and-forget.
    - **Validation is allow-list based** (`analytics/validation.ts`): fixed event names, capped prop count, capped value/path/session lengths, capped batch size, non-scalar prop values dropped rather than stringified, and a client clock more than 24h from server time clamped. `/api/events` is a public unauthenticated write endpoint, so this parser is the only thing keeping the table bounded.
    - **Ingest failures answer 204, not an error.** A dropped analytics batch must not surface as a broken request in a visitor's console, and the client has nothing useful to do about it.
    - **What this is honestly worth:** raw, queryable, first-party data you own — enough to answer "what are people searching for that we don't stock?" (`0003_analytics_events.sql` ships that query and four others in its footer). It is **not** a monitoring product: no dashboards, no alerting, nothing pages anyone. If errors ever need to trigger a response rather than be looked up afterwards, Sentry/PostHog is the answer and `eventStore.ts` is where it attaches.
    - **Zero-result searches are the highest-value signal here** — a ranked, user-written list of what the catalog is missing. Use it to prioritise Batch 7 rather than guessing.

30. **The Privacy Policy and Terms (`/privacy`, `/terms`) describe what the code actually does, and `legal.test.ts` keeps them honest.** Every business-specific value is in `src/lib/legal.ts` (7 placeholders as of 2026-08-21; both pages self-mark as "being finalised" until they are filled). **If you add a `localStorage`/`sessionStorage` key, a lead field, or an analytics event, update the policy in the same commit** — the test scans `src/` for `ev-motion:*` literals and fails on any undisclosed key, and fails if `document.cookie` ever appears (the policy states the site sets no cookies, which is why it has no banner). It caught a missing sixth storage key on its first run. **Not legally reviewed** — accurate is not the same as sufficient.

31. **Error monitoring and lead notifications are both OPTIONAL and both no-op when unconfigured — that is a supported state, not a broken one.** Added 2026-08-21.
    - **Sentry** (`src/lib/monitoring/sentry-config.ts` owns the config; `src/instrumentation.ts` + `src/instrumentation-client.ts` are the Next 16 entry points). With no `NEXT_PUBLIC_SENTRY_DSN`: no init, `next.config.ts` skips `withSentryConfig` entirely, and **the browser never fetches the SDK chunk** — measured at **319 KB of JS without vs 503 KB with**, so the bundle diet of CLAUDE.md #23 is preserved for anyone not using it. Verified both ways with a dummy DSN, including a real captured error reaching the `/monitoring` tunnel.
    - **`tunnelRoute: "/monitoring"` is load-bearing**, not decoration: ad blockers block `sentry.io` by default, which would silently swallow exactly the reports you installed it for.
    - **`scrubEvent` must keep stripping `request.data`, cookies and IP headers.** Sentry attaches request bodies by default, and a lead POST body is a name, phone and email. `/privacy` states we do not log those, so this is what keeps that page true — `monitoring.test.ts` asserts no PII survives.
    - **`sendDefaultPii` stays `false` and Session Replay stays off.** Both would contradict `/privacy`; turning either on is a policy change first and a code change second.
    - **Server errors are now captured even without Sentry**, via `onRequestError` -> `lib/monitoring/serverErrors.ts` -> `analytics_events`. That closed a real gap: client errors have been captured since 2026-08-16, but server errors went only to the platform log.
    - **Lead notifications** (`src/lib/leads/notify.ts`, `LEAD_WEBHOOK_URL`) — a generic webhook, so one variable covers Slack/Discord/Chat/Teams/Zapier with no new vendor account. **Ordering is load-bearing: store first, notify second.** The notifier never throws and times out at 2.5s, so a dead webhook costs the alert and never the enquiry. It does send the submitter's contact details, so the destination must be a private channel — that is why `/privacy` names service providers.

32. **`--ink-muted` is `#767676` in `:root` and `#94a3b8` in `.dark` — both deliberate, do not "simplify" them back to one value.** The light value was darkened from `#909090` on 2026-08-21 because 3.19:1 on white fails WCAG AA; the dark override exists because `.dark` only ever redefined the shadcn tokens, so `--ink-muted` used to fall through to the light value and the darker grey would have failed on the dark background instead. **A text colour needs a value per surface.** `--chart-4` stays `#909090` on purpose: it tints chart geometry, not text. Two contrast groups are still open and documented in HANDOFF.md — muted text on off-white panels (4.2-4.4:1), and the brand green `#1fa83c` used at body size (3.12:1), which is a design decision rather than a token swap.

## Known intentional limitations (not bugs)

Commercial-EV category has real architecture but zero data (see above). One research staging file (`_research-commercial.ts`, for Batch 5) contains real unmerged vehicle data — `_research-two-wheelers.ts` was fully merged and deleted at the end of Batch 4. Car dataset covers Tata/Mahindra/MG/Hyundai/Kia (Batch 1) plus BYD/BMW/Mercedes-Benz/Audi/Volvo/MINI/Porsche/Lotus/Rolls-Royce/VinFast (Batch 2) — 54 records, 15 car OEMs. Two-wheeler dataset covers all Batch-3 scooter brands plus Batch-4 motorcycle brands — 69 records (55 scooters + 14 motorcycles), 31 two-wheeler OEMs (the 69th, Chetak C3503, was added by sub-batch 9's Bajaj line-up reconciliation). **Two of those 69 are `discontinued` and so are not listed** (`bajaj-chetak-2901`, `bajaj-chetak-premium`), which is why the catalogue is 123 vehicles but `/two-wheelers` shows 67 and the site lists 121 — see point 29. Commercial EVs is not started (Batch 5). **No vehicle has real photo data** — every `photoUrl` was intentionally removed in the production polish pass and none has been re-added; sourcing real licensed photography is still the outstanding step. Since 2026-08-17 cards render a **generic AI illustration of the vehicle's body type** where one has been generated (5 of 6 types; scooters still on the SVG icon), falling back to the branded placeholder otherwise — see point 26, and note that neither is a photo of the vehicle and neither populates `photoUrl`. **ImageKit is a live delivery integration** for those illustrations; `photoUrl`/`gallery` on `VehicleImages` remain empty and reserved for real photography. **Supabase is a real backend for lead capture and analytics** (points 24-25), not the inert MCP config this file used to describe. Multi-word search queries that skip a word or an informal brand-name shortening (e.g. "simple ultra", "Tata Nexon" for a record whose `oemName` is "Tata Motors") return no results — pre-existing `search.ts` characteristic, still open (flagged as a Future Roadmap item in `HANDOFF.md`). "Portable Battery" isn't a filterable field despite being requested for Batch 3 — needs a schema change, flagged not done. Ad slots are static placeholders, no pagination yet, Reviews/Latest News (including the new homepage "Latest EV News" section) are honest empty states with working forms behind them, no backend for anything beyond leads and analytics, placeholder SEO domain, a few shadcn primitives left unrestyled (`Tabs`, `Popover`/`Command`). Full reasoning for each is in `HANDOFF.md`'s Known Limitations section.
