## PROJECT OVERVIEW

### Project purpose

EV Motion is an Indian electric-vehicle marketplace demo — a CarWale/BikeWale-style site for browsing, filtering, comparing, and searching electric vehicles. It began as an original build ("EV Wale") with its own 36-vehicle dataset, was reskinned to match a supplied "EV Motion" design template, went through a full production-readiness QA cycle, had a session that replaced every remaining visual-only interaction (location, filters, search) with real, working logic and generalized the codebase from a hardcoded car/two-wheeler binary into a genuine N-category system — adding **commercial EVs** (3-wheelers, small trucks/LCVs, vans, buses) as a first-class third category — and most recently went through a **production polish pass**: a fresh, ground-up audit (not just a fix-the-known-list pass) covering navbar, location, search, filters, images, model pages, price/subsidy tooling, homepage sections, and compare, which found and fixed a page-wide CSS layout bug and a search-navigation dead-end that the earlier sessions had missed. It has no backend — all data is static TypeScript, and every "submit" action (lead capture, reviews) is a local, honestly-labeled demo interaction.

### Tech stack

- **Next.js 16** (App Router, Turbopack) — ⚠️ this version has real breaking changes vs. training-data assumptions; see `AGENTS.md` / `node_modules/next/dist/docs/` before writing App Router code. `params`/`searchParams` are `Promise`s that must be `await`ed, and generated `PageProps<'/route/path'>` / `LayoutProps<...>` global types exist and are used instead of hand-written prop shapes.
- **React 19**, **TypeScript** (strict — `npx tsc --noEmit` is part of the project's quality gate)
- **Tailwind CSS v4** — theme defined via a `@theme` block in `src/app/globals.css`, not a `tailwind.config.js`
- **shadcn/ui on Base UI** (not Radix) — see [Architectural Decisions](#architectural-decisions) for the `render`-prop implication
- **framer-motion** (page transitions, card hover, gallery animations), **lucide-react** (icons), **cmdk** (compare page's vehicle picker command palette)
- No backend, no database, no auth, no new dependencies added since the original QA cycle — 100% static data + client-side interactivity

### Architecture overview

This is a **static-data-driven Next.js App Router site**. There is no API layer — every page imports directly from `src/lib/data/*` at build/request time. Pages fall into two render strategies:
- **Static (SSG)**: homepage, all vehicle VDPs, all brand pages, `/brands` — pre-rendered at build time via `generateStaticParams`.
- **Dynamic**: `/cars`, `/two-wheelers`, `/commercial`, `/compare` — server-rendered per-request because they read `searchParams` for filter/compare state.

The key architectural change this session: the app used to hardcode "car" and "2-wheeler" as two parallel, hand-written code paths almost everywhere (brand-page sections, sitemap routes, compare tabs, the homepage's card/listing builders, the VDP's derived-spec formulas). That's been replaced with a **category registry** (`src/lib/data/categories.ts`) that every one of those places now loops over. The practical result: `/commercial` exists as a fully working route tree, listing page, VDP, filter config, search scope, brand-page section, and compare tab — with **zero vehicle records in it yet**. Adding real commercial vehicles requires inserting records into `src/lib/data/commercial.ts` (and matching OEM records into `oems.ts`) — no page or component code needs to change, which was the explicit design goal.

### Design system overview

Defined in `src/app/globals.css`'s Tailwind v4 `@theme` block — no separate config file:
- **Color tokens**: `primary` (green `#1FA83C`, + `-hover`/`-tint`/`-bright` variants), `ink`/`ink-secondary`/`ink-muted` (text), `surface`/`surface-secondary`/`surface-dark` (backgrounds), `border`/`border-strong`, semantic `hot`/`info`/`warning`/`error`.
- **Shadows/animation**: `shadow-card`, `shadow-card-hover`, `shadow-popover`, `animate-fade-in`, `animate-pulse-dot`.
- **Utilities**: `.focus-ring` (consistent focus-visible ring used on every interactive element), `.scroll-row` (horizontal-scroll carousel styling), `.line-clamp-*`.
- **Typography**: Inter (via `next/font/google`), applied through pixel-precise Tailwind arbitrary values (`text-[13px]`, `text-[11px]`, etc.) rather than the default `text-sm`/`text-xs` scale.
- shadcn's own semantic CSS variables (`--primary`, `--background`, etc.) are **repointed to the same palette**, so any shadcn primitive still in use (Select, Slider, Checkbox, Sheet, Tabs, Popover, Command, Dialog) already renders in the correct brand colors without needing to be rewritten. **No design-token or visual-language changes have happened in any session, including the 2026-08-15 homepage redesign** — everything new since the original build (LocationSelector, ResponsivePopover, the commercial placeholder icon, and every new homepage component from the 2026-08-15 pass) was built strictly within this existing token system: light/white `surface` backgrounds, the green `primary` palette, `surface-dark` reserved for a small number of deliberately dark accent cards (Featured Banner, Key Highlights, sidebar Advertiser, Upcoming cards), never as a whole-page theme. **This is now a locked decision, not just an observation — see [Design System — Locked Decisions](#design-system--locked-decisions-do-not-revert).**

The rest of this paragraph's described behaviour is unchanged — but note the workaround it mentions below (curated terms restricted to bare model names because "OEM full name + model" could never match) is no longer *necessary*, only still true of the current term list. Debounced (180ms) matching, plus a **Levenshtein-distance typo-tolerance fallback** when no substring match is found, plus keyword routing for category terms (including commercial terms — "truck", "3-wheeler"/"auto", "van", "bus") straight to the real listing filters. Shows **recent searches** (localStorage) and **curated popular searches** when focused with an empty query. Category-keyword matches ("SUV", "Scooter", …) are resolved ahead of incidental substring vehicle-name matches, so "SUV" correctly lands on `/cars?type=suv` rather than a random vehicle whose name happens to contain "SUV". Keyboard support (↑/↓, Enter, Escape, click-outside) now also works on the Recent/Popular suggestions panel, not just live results. ## PREMIUM COMPARE PAGE (2026-08-01)

`/compare` was rebuilt from a bare-bones spec table (unrestyled tabs, a cmdk popover picker, a 9-row grid) into a full Apple/Tesla/Rivian-inspired comparison experience, while staying built from the site's existing design tokens and component patterns — not a redesign of anything else. Full detail, QA evidence, and a component/feature inventory: **`COMPARE_PAGE_REPORT.md`** at the repo root. Summary here:

**URL structure — a genuinely new routing pattern for this codebase.** Every other dynamic route (`cars/[slug]`, `two-wheelers/[slug]`, `commercial/[slug]`, `brands/[oem]`) uses a single plain segment with `generateStaticParams()` enumerating the full finite set. Compare needed something different: `/compare/tata-nexon-ev-vs-mg-windsor-ev` (2 vehicles) or `.../...vs-mahindra-be-6` (3 vehicles), via a new `src/app/compare/[slug]/page.tsx` that **deliberately has no `generateStaticParams`** (the combinatorial space — C(54,2)+C(54,3) for cars alone — is far too large to pre-render; renders on demand instead). `src/lib/compare/slug.ts` owns `buildCompareSlug()`/`parseCompareSlug()` (`MAX_COMPARE = 3` lives there as the single source of truth) — the parser defends against a hypothetical future vehicle slug containing the literal `-vs-` delimiter by trying every valid split point, not just a naive single split. The legacy `?ids=slug1,slug2` contract (6+ site-wide entry points depend on it: homepage `CompareCard`, every `VehicleCard`'s "Add to Compare", VDP `VehicleHero`, VDP `SectionCompareSimilar`, footer link) still works — `src/app/compare/page.tsx` resolves it and redirects to the canonical URL when 2-3 valid same-category vehicles resolve.

**Data honesty — the load-bearing design constraint.** The spec asked for Safety/NCAP/ADAS, Dimensions, Warranty, Features, and Ratings — none of which existed anywhere in the original `Vehicle` schema. Rather than reuse `toVehicleDetail.ts`'s existing computed-approximation convention (power/torque formulas, hardcoded per-category warranty — which stays exactly as-is for the VDP), a new parallel `Vehicle.specs` field was added (`src/types/vehicle.ts`) that is **real, sourced data only, optional at every level, populated for a researched 15-vehicle pilot batch** (see "Batch 6" in the batch log below) — everywhere else it's `undefined`, and every UI surface reading it renders "Not officially specified" rather than guessing. Pros/Cons and Expert Verdict are similarly computed, not authored: Cons are the vehicle's actual losing metrics from the winner engine ("Lower range than the Nexon EV"), not invented qualitative claims; Expert Verdict is templated neutral copy generated from real winner tallies + price comparison.

**Winner engine** (`src/lib/compare/winnerEngine.ts` + `metrics.ts`) — a generic, growing registry: `SPEC_ROWS`-shaped arrays (one per section) drive every spec table's rendering, a single flat `WINNER_METRICS` array (spanning every section, so the "wins N categories" tally is genuinely cross-section) drives crown badges, the Winner Ribbon, RatingsSection, and SmartRecommendation. **A metric only crowns a winner with ≥2 known values** — a single known value among unresearched vehicles has nothing real to have beaten, so it's "insufficient data," not an automatic win (a real bug hit and fixed during QA — see `CLAUDE.md` point 15). Adding a new real spec field later is a registry entry, not a new component.

**New shared infra**: `src/lib/pricing.ts` (`onRoadPriceBreakdown()` — extracted from two previously-duplicated inline copies in `SidebarPriceSummary.tsx`/`SectionCompareSimilar.tsx`, both refactored to use it; `calculateEmi()`; `estimateMonthlyChargingCost()` — *this file no longer exists; fully merged into `src/lib/vehicle-pricing/` during the later Site-Wide Centralized Pricing Architecture pass, see that section*), `src/lib/search-history.ts` (recent-search persistence, extracted from `VehicleSearchBox.tsx` so `ChangeVehicleModal` doesn't duplicate it), `AdSlot` promoted from `vehicle-detail/` to `src/components/common/` since it's now used by two feature areas.

**PDF export** (`src/lib/pdf/`) — the project's first new npm dependency since the original QA cycle (`jspdf` + `jspdf-autotable`, user-approved exception). `pdfKit.ts` holds plain-data primitives (no `Vehicle`/`VehicleDetail` types in any signature) so a future report elsewhere in the app could reuse them; `generateComparePdf.ts` assembles the Compare-specific report from already-computed data; `buildComparePdfInput.ts` is the glue that reuses the same `SPEC_ROWS` render functions the web UI uses, so the PDF can't drift from what's on screen.

**A real bug found and fixed during QA**: this repo's local `CommandDialog` (`src/components/ui/command.tsx`) only provides the Dialog shell, unlike the upstream shadcn convention — it does not wrap children in cmdk's `<Command>` store provider. `ChangeVehicleModal.tsx` initially omitted that wrapper and crashed at runtime (`Cannot read properties of undefined (reading 'subscribe')`) the moment "Change Vehicle" was clicked; found via live browser testing, not caught by `tsc`/`eslint`/`build`. Fixed by wrapping in `<Command>` explicitly — flagged in `CLAUDE.md` point 14 so it isn't reintroduced.

**Quality gate**: `npx tsc --noEmit`, `npx eslint .`, `npm run build` all clean (still 179 routes — `/compare/[slug]` is dynamic, not statically enumerated, by design). Verified live: 2- and 3-vehicle comparisons for both cars and two-wheelers, the legacy `?ids=` redirect, an invalid slug's honest 404, every entry point's generated URL, city-switching live-recomputing the price breakdown, the EMI/charging calculators, the Change Vehicle modal (post-fix), PDF download triggering with no console errors, and all three JSON-LD blocks (`ItemList`/`BreadcrumbList`/`FAQPage`) parsing as valid JSON. **One verification gap**: this session's browser-automation tooling reported an inconsistent mobile viewport (`window.innerWidth` stuck at 460px regardless of resize commands, and `screenshot` failed with "Browser pane is not displayed") — layout-tree-based checks (`elementsFromPoint`, computed `flex-direction`, scroll-container own-width vs parent-width) all came back clean with no evidence of real overflow, but this wasn't confirmed with an actual rendered screenshot. Worth a quick visual pass next session once screenshot tooling is available.

The pilot-vehicle data research behind `Vehicle.specs` is logged as **Batch 6** in the Full-Market Expansion batch log below (same section as Batches 1-5), not repeated here.

## SITE-WIDE CENTRALIZED PRICING ARCHITECTURE (2026-08-02)

**This section replaces an earlier, same-day "Vehicle Detail Page — Centralized Pricing System" pass.** That first pass built a VDP-only pricing system deliberately kept separate from the Compare page/homepage, and its price card design still showed a prominent on-road breakdown with an explanatory info box. A follow-up brief the same day corrected both calls: (1) the VDP price card read as visually heavy and needed a compact, CarWale-style redesign, and (2) — the real bug — **changing city updated the displayed city name everywhere but not most displayed prices**, because only the on-road *extras* (registration/tax/insurance) were ever city-aware; the ex-showroom price itself was a flat catalog number on every page except the VDP's own sidebar widgets. This pass fixes both and, per the corrected brief, extends centralized pricing to the *entire site*, retiring the VDP/Compare split from the first pass.

### What changed vs. the first pass

- The VDP's `pricing.ts` vs. `vehicle-pricing/` split is gone. **`src/lib/pricing.ts` no longer exists** — `calculateEmi` and `estimateMonthlyChargingCost` moved into `src/lib/vehicle-pricing/emi.ts` and `chargingCost.ts`, and every former consumer (Compare's `PriceSection`, `OwnershipSection`, `EmiCalculator`, `VehicleSlotCard`, `ratings.ts`, `buildComparePdfInput.ts`) now imports from `vehicle-pricing/` — there is exactly one pricing module for the whole site now.
- Ex-showroom price itself now varies by city (see "City Pricing Service" below) — not just the on-road extras layered on top of it.
- The VDP price card is compact: no on-road figure, no green info box, no bullet list — see "Redesigned VDP price card" below.
- Pricing sync now reaches the homepage (Featured Vehicle, popular/ranked/compare-pair cards), listing pages, brand pages, and the Compare page (price table, ownership cost, EMI, PDF export) — all previously showing a static, city-invariant ex-showroom figure.

### The "City Pricing Service" — why a formula, not a 150-city × 122-vehicle table

`src/lib/vehicle-pricing/cityPriceZones.ts` adjusts a vehicle's base catalog ex-showroom price for the selected city. A literal per-city-per-vehicle price table would need ~19,000 hand-authored, unsourced numbers (157 cities × 122 vehicles) — this app has no backend or manufacturer feed to source real numbers from, so that would look precise while being pure invention. Instead, same honesty convention as `state-charges.ts` ("estimated, not sourced from a live API"), the adjustment is a small, explainable two-factor formula:

1. **Per-state logistics zone** (`STATE_ZONE_PCT`) — states with the biggest EV/auto manufacturing and dealer networks (Delhi-NCR, Maharashtra, Gujarat, Tamil Nadu, Karnataka) sit closest to 0%; farther states carry a progressively larger estimated freight premium, up to Ladakh/Andaman & Nicobar/Lakshadweep at the top (3.5-4.5%).
2. **Non-metro tier extra** (+0.5%) — any city outside `cities.ts`'s curated `popular` metro set gets a small additional bump (smaller dealer volume, longer last-mile logistics).

A handful of Delhi-NCR satellite cities (Noida, Gurugram, Ghaziabad, Faridabad) are pinned to Delhi's own 0% via an explicit override — they sit in UP/Haryana's state zone on paper but are realistically the same logistics catchment as Delhi. Every value renders through UI copy labeled "estimated," same convention as the rest of the pricing system. `cityAdjustedExShowroomRange(baseRangeLakh, city)` applies the resulting % to a vehicle's `[low, high]` catalog range, rounded to ₹0.01L. All 42 cities named in the brief (and the rest of `cities.ts`'s 157) resolve to a real, non-identical, non-blank number — verified live for Chennai (+0.25%) and Leh/Ladakh (+5% combined), see Verification below.

### Pricing state flow (single source of truth, now site-wide)

```
useLocation() (LocationContext, global/localStorage-persisted)
        │  { city }
        ▼
useVehiclePricing(vehicle)  ──calls──▶  getVehiclePricingSnapshot({ vehicleId, vehicleName, exShowroomRangeLakh, city })
        │                                        │
        │                              cityAdjustedExShowroomRange(base, city) → adjusted ex-showroom
        │                              chargesForState(city.state) → StateCharges
        │                              calculatePriceRangeBreakdown(adjusted, charges) → on-road
        │                              estimateEmiFrom(adjusted low end) → EMI
        ▼
VehiclePricingSnapshot { cityName, stateName, baseExShowroomRangeLakh, exShowroomRangeLakh (adjusted),
                         breakdown: {low, high}, emiFromPerMonth, lastUpdated }
```

`src/lib/vehicle-pricing/subject.ts`'s `vehiclePricingSubject(vehicle)` adapts any raw catalog `Vehicle` into the hook's plain `{id, name, priceRangeLakh}` shape — deliberately **not** in `useVehiclePricing.ts` itself, because that file is `"use client"` and a "use client" file's exports can't be *called* (only rendered) from a Server Component; `vehiclePricingSubject` needs to be callable from Server Components like `ListingCard`/`RankedListCard`/`CompareCard` (hit this exact error mid-build — `next build` failed with "Attempted to call vehiclePricingSubject() from the server but vehiclePricingSubject is on the client" — before the fix).

Two small client leaf components, `src/components/pricing/VehiclePriceText.tsx` and `VehicleEmiText.tsx`, are the drop-in replacement for every static `priceLabel`/`emiLabel` string that used to be pre-computed server-side: they take a plain, serializable `VehiclePricingSubject` prop (no functions) and call `useVehiclePricing` internally, so they're safe to embed inside Server Component card trees (`ListingCard`, `RankedListCard`, `CompareCard`, `SimilarComparisonsCarousel`, `SimilarCarCard`) without converting those cards themselves to client components.

### City pricing flow

Unchanged from the first pass: "Change City" mounts the existing `LocationSelector` locally (controlled component, no new city-picker UI). Selecting a city calls `LocationContext`'s `setCity()` → persists to `localStorage` → every mounted `useVehiclePricing()` call recomputes on next render. `chargesForState()` and `cityPriceZone()` both fall back gracefully (`DEFAULT_CHARGES`, `DEFAULT_ZONE_PCT`) for any state not explicitly listed — never a blank price.

### Batch 5 — Real lead capture ✅ DONE

**This is the first genuinely non-static thing in the project.** Every CTA previously validated its inputs and set `submitted = true`; leads are the revenue model for a marketplace, so this was the wall between the project and being a product.

`POST /api/leads` is the single entry point behind all six CTAs (`GetBestPriceDialog`, `FeaturedBanner`, `AdvertiseSection`, `SidebarAdSlot`, `UpcomingCard`, `UpcomingNotifyBanner`). Order is **rate-limit → honeypot → validate → store**; nothing reaches the database before validation.

- **`src/lib/leads/`** — `types.ts`, `validation.ts` (shared with the dialog, but the server copy is the actual gate and is allow-list based, so unknown `fields` keys are dropped rather than passed through), `rateLimit.ts`, `leadStore.ts` (the seam, same pattern as `vehicle-pricing/pricingSource.ts`), `supabaseLeadStore.ts`.
- **Supabase over PostgREST with `fetch`, not `@supabase/supabase-js`** — a single INSERT, a dozen lines, and it keeps a dependency out of a project with no backend libraries. Swapping later means rewriting one file.
- **`public.leads` has RLS enabled with zero policies** (`supabase/migrations/0001_leads.sql`), denying anon and authenticated outright; the app writes with a secret key that bypasses it. `0002_…_publishable_key_policy.sql` exists as an *alternative* for publishable-key setups and grants INSERT only — read the trade-off in its header before running it.
- **Leads are never logged.** The route logs only the store's error message, which is PII-free by construction.
- **When the env vars are absent the endpoint returns `not-configured` and the dialog says so** rather than showing a confirmation it can't back up. This is deliberate and matches the project's honesty convention — someone handing over their phone number is owed an accurate answer.

**Verified end to end against the live project** (`dzloqeyqpddjcyxzsvcz`): a submission through the UI on `/cars/mg-windsor-ev` landed with `kind`, `vehicle_slug`, `city` and `source_path` populated, unicode intact (`Ananya Rāo — UI test`), and the mobile normalized from `+91 98765-00003`. RLS confirmed enforcing: with 5 rows in the table the publishable key saw **0** and its inserts failed with `42501`. Test rows were deleted afterwards; the table is empty.

**Two migration bugs found and fixed by running it for real:**

1. `date_trunc('minute', created_at)` on a `timestamptz` is **STABLE, not IMMUTABLE** (it depends on the session `TimeZone`), so Postgres rejected the dedupe index with `42P17`. Fixed as `date_trunc('minute', created_at at time zone 'utc')`, which selects the IMMUTABLE `date_trunc(text, timestamp)` overload. The `at time zone 'utc'` is load-bearing, not decoration.
2. A unique index means a double-click raises a 409, which the route would have surfaced as a failure for what is actually a successful submission. The insert now sends `Prefer: resolution=ignore-duplicates` (→ `ON CONFLICT DO NOTHING`), with a 409 check as a fallback. Verified: three identical back-to-back submissions produce **one row**, all reporting success.

**Known limitation, stated plainly:** the rate limiter is in-memory and therefore **per-instance**, not global — it resets on redeploy and an attacker spreading requests across instances gets a proportionally higher effective limit. It raises the cost of casual form-spamming; it is not a flood defence. `rateLimit.ts` documents the shared-store upgrade path.

### Batch 6 — Analytics and error reporting ✅ DONE

Nothing recorded what people searched for, which comparisons they ran, which CTAs converted, or what broke in production. `RouteError` logged to the console with a `TODO` pointing here.

`POST /api/events` takes five events — `search` (with query and result count), `vehicle_view`, `compare_view`, `lead_submitted`, `error`. Page views go through a `TrackPageView` client leaf so pages stay Server Components. **Verified end to end against the live database: all five land with correct props.**

**The privacy posture is the design, not a default**, and four properties hold it together — breaking any is a privacy-policy decision, not a code change:

- **No cookies, no durable identifier.** The session id lives in `sessionStorage`, dies with the tab, and can't recognise a returning visitor or follow anyone across sites. That is what lets the site run analytics *without a consent banner*.
- **No IP stored.** The route rate-limits with it and discards it.
- **No PII in payloads.** Verified live, side by side: one submission wrote `{kind, vehicleSlug}` to `analytics_events` while the name and mobile existed only in `public.leads`.
- **`analytics_events` is RLS-deny-all**, same as `leads`. Verified: the publishable key saw **0 of 6** rows.

`track()` never throws and never blocks — every entry point swallows its own errors; events queue and flush on a timer or at page-hide via `sendBeacon`. Ingest failures answer **204**, so a dropped batch never surfaces as a broken request in a visitor's console. Validation is allow-list based (fixed event names, capped prop count, capped lengths, capped batch size, non-scalar values dropped rather than stringified, client clocks >24h out clamped) — `/api/events` is a public unauthenticated write endpoint, and that parser is the only thing keeping the table bounded.

**A real bug was found by reading the table rather than the code:** a single page load had written two `vehicle_view` rows 3ms apart, because React StrictMode double-invokes effects in dev. A production build fires once — but it silently doubled counts for anyone browsing their own dev server, and any future remount would do the same in production. `track()` now suppresses an identical event repeated within 1s, which absorbs a remount while leaving a genuine repeat visit or repeated search intact.

`0003_analytics_events.sql` ships five queries in its footer. **The one that matters most is zero-result searches** — a ranked, user-written list of what the catalog is missing, and much better input for Batch 7 than guessing. It already has a real entry.

**What this is not:** raw first-party data, not a monitoring product. No dashboards, no alerting, nothing pages anyone. If errors ever need to *trigger* a response rather than be looked up afterwards, Sentry/PostHog attaches at `eventStore.ts`.

## BATCH 7, SUB-BATCH 2 — 2026-08-17: SPECS + AI ILLUSTRATIONS

Branch `batch-7-specs-and-ai-illustrations`, commit `0e09636` plus this docs commit. Not merged, not pushed. Quality gate clean throughout: **167 tests**, `tsc`, `eslint`, `npm run build` (421 routes, unchanged).

### Specs: 18 → 23 of 122

Tata **Harrier EV** and **Sierra EV** (completing Tata's 7 cars), Mahindra **XEV 9e** and **XUV400**, Hyundai **Creta Electric**.

**Prioritisation, and why it isn't arbitrary.** The obvious plan is "most popular vehicles first," but the payoff structure argues for clustering by OEM. `winnerEngine.ts` needs **≥2 known values** before it crowns anything, and `getRelatedVehicles()` — the function that generates the 241 pre-rendered comparison pages — pairs **same-OEM first**. So specs value is superlinear in clustering: five vehicles spread across five brands leave almost every comparison still one-sided, while five that complete a brand populate *both* sides of that brand's whole comparison set. Tata was 5/7 done, so finishing it was the cheapest large win available.

The handoff suggests using `0003_analytics_events.sql`'s zero-result-search query to prioritise. That was checked and **is not yet usable**: the table holds only a handful of rows from local testing, so it carries no real traffic signal. Revisit once the site has actual visitors — the query is right, the data isn't there yet.

**Every omission is recorded inline in `cars.ts` with its reason.** The four that generalise to the remaining 99:

1. **The Sierra EV has no NCAP rating, on purpose.** It has not been crash-tested. The 5-star Bharat NCAP result every aggregator shows next to it belongs to the **petrol Sierra**. This is the third time this exact trap has appeared (Tiago EV, Punch EV, now Sierra EV) and it is the single most likely way a fabricated safety claim gets into this dataset. **The structural tell: if a model has an ICE twin, assume a quoted rating is the twin's until proven otherwise.** Where a model is born-electric with no petrol version — XEV 9e, BE 6 — a quoted rating can only be the EV's, and is safe.
2. **Widths are body widths, excluding mirrors.** The Harrier EV's widely published width is **2132mm**, which is the with-mirrors figure; its body is **1922mm**. The existing records use the without-mirrors convention (Nexon EV 1811mm), so writing 2132 would have made the Compare page's Width row measure one car with mirrors against everything else without, and crowned a false winner. Check which convention a source is using before recording a width.
3. **Power gets omitted when the sources don't reconcile.** Harrier EV (313hp per Autocar vs a 390bhp "Boost Mode" figure, and RWD/AWD differ) and Sierra EV (306hp, no published kW, 504Nm is QWD-only) both got no power or torque. Where power *is* recorded it reconciles across units: XUV400's 110 kW is simultaneously the quoted 147.51 bhp and 149.55 PS — which also exposed an aggregator printing that PS number in a kW column as "149.55 kW".
4. **Conditional battery warranties stay out.** Both Tata and Mahindra now sell "lifetime for the first owner, N years if transferred" schemes. `VehicleWarranty`'s single-number-per-field shape cannot express that without misrepresenting one owner or the other, so battery terms are absent while unambiguous motor/vehicle terms are recorded. This is now the **norm** among Indian OEMs, not an edge case — the schema gap flagged in Batch 6 is worth closing before a large follow-up batch.

**One correction to existing data.** BE 6's `peakPowerKw` was **213**; Mahindra's own launch press release states **210 kW** for the 79 kWh pack, and 213 was a back-conversion of the quoted 286 PS. BE 6 and XEV 9e share that exact powertrain, so a 3 kW rounding artifact was enough to hand BE 6 a **false Power crown over its own sibling** — the pairing those two vehicles are most likely to appear in. Corrected on both records together, and both gained the officially stated `batteryChemistry: "LFP"`. Worth internalising: an error of this size is invisible on a spec sheet and decisive in a winner engine.

```
ik-genimg-prompt-<prompt>/…      text-to-image, flat vector on white
   ?tr=e-bgremove,f-png          transparent PNG cutout
   -> upload to /illustrations/vehicle-types/<key>.png   stable library path
```

All three stages are ImageKit-native, so **no external image is ever fetched, downloaded or copied** — which is the whole point, given the production polish pass deleted every photo to remove exactly that exposure. No new dependency: the upload is plain multipart `fetch`, the same choice `supabaseLeadStore.ts` makes for Supabase.

**Why assets are persisted instead of served straight off the `ik-genimg` URL.** Delivering the generation URL would embed the entire prompt in every page's HTML, re-run a paid and **non-deterministic** generation on any cache purge (so the picture could silently change), and make the URL churn whenever a prompt is edited. A committed path is stable, cacheable and reviewable.

**The honesty boundary — this is the part to not get wrong.** Three rules, all enforced by tests, all explained at length in the module header:

- **Per body type, never per model.** Every SUV in the catalog shares one drawing. That is what makes it honest: a visitor sees the same picture on the Nexon EV and the Windsor EV and reads it as category art, exactly the way the hand-drawn SVG icon it replaces was read. It is a better-crafted placeholder, not a photo. Six illustrations cover all 122 vehicles.
- **`Vehicle.images.photoUrl` stays empty, and stays reserved for real licensed photography.** AI art upgrades the *placeholder* layer only. This is why the "0 of 122 photographed" row in the status board is still accurate and must not be marked done.
- **Never photoreal.** The first probe asked for a photorealistic generic electric car and returned a **near-copy of a specific real production SUV's design** — unmistakably one manufacturer's car — because that is what the model was trained on. A photoreal "generic EV" is a trade-dress problem wearing a disguise. The style string's `not photorealistic` and `no logos / no badges / no brand marks / no number plate` clauses are load-bearing; `vehicle-illustrations.test.ts` fails if any is removed, and separately scans every subject prompt for any real OEM or model name.

Those guards were **mutation-checked** in the project's usual style: injecting "Tata Nexon" into a subject prompt fails two tests by name.

**Integration.** `PlaceholderImage` gained the sub-type props and renders the cutout over the existing per-OEM brand gradient (so cards keep their colour variety), falling back to the SVG icon when no illustration exists. `VehicleImageSubject` gained three optional sub-type fields, so a full `Vehicle` gets an illustration automatically at every one of `VehicleImage`'s ~15 call sites with no per-call change. A `VehicleIndexEntry` has no sub-type, so **search thumbnails keep the SVG icon** — correct at 44px, and it avoids adding anything to the 22 KB search index (Batch 2 discipline).

Accessible names disclose it: *"Tata Motors Harrier EV — generic SUV illustration, not a photograph of this vehicle."* The sub-type label is read from `vehicle-filter-options.ts`'s own `subTypeOptions` rather than a second hand-written list.

### Two smaller things worth knowing

- **`tsconfig.json` gained `allowImportingTsExtensions: true`.** `scripts/*.mts` run directly under Node's native type stripping (Node 24), which *requires* the explicit `.ts` extension on relative imports, while `tsc` rejects it by default. Safe because `noEmit` is already on, and it keeps those scripts inside the typecheck instead of excluding `scripts/` from it. The `.mts` extension is also deliberate — it marks the file ESM so Node doesn't warn about the package's CommonJS default on every run.

### The finding: hub-motor torque and mid-drive torque are different quantities

**All three TVS records get no `peakTorqueNm`, and this is a measurement-convention problem rather than a sourcing one.**

TVS quotes **140 Nm** for the iQube. That is **hub-motor torque, measured at the wheel**, with no gear reduction between motor and road. Ather, Ola and the other mid-drive scooters quote **shaft torque**, which their belt drive then multiplies before it reaches the wheel. The two numbers describe different points in the driveline and are not comparable.

Dropping 140 into the same Compare Torque row as the 450X's 26 Nm would crown the iQube by roughly **five times**, on a difference that is purely definitional. This is structurally identical to the width-with-mirrors trap in CLAUDE.md #28(b): two real figures, two conventions, one meaningless winner.

1. **Omit it too**, matching the three records added here. Cheapest, loses a real published figure.
2. **Add a convention field to `VehicleMotor`** — e.g. `torqueMeasuredAt: "shaft" | "wheel"` — and have `metrics.ts` refuse to compare across conventions. Most correct, and it generalises: the same shape of problem will recur wherever OEMs measure differently.
3. **Exclude torque from the two-wheeler winner metrics entirely**, keeping it as a displayed spec but not a scored one. Middle cost, and defensible on its own terms since torque is a poor single-number proxy for scooter performance anyway.

`ampere-nexus` should be checked for the same issue when this is decided.

## HOMEPAGE HERO — 2.5D VEHICLE + ENVIRONMENT (2026-08-18)

The homepage hero gained a vehicle and a lit environment. This is the **first change to the hero since the 2026-08-15 redesign** and it was explicitly requested and iterated on by the owner, so it supersedes the "Hero is image + headline only" description in the redesign section above. **Sub-`lg` the hero is untouched** — same 300px height, same centred copy, same background — every change here is `lg` and up.

### What it is now

At `lg` and above the hero renders four stacked layers, all driven by one rAF loop that writes two CSS custom properties (`--hero-px` / `--hero-py`, each −1..1) onto `[data-hero-root]`. Every layer consumes the same pair with a different multiplier, which is what produces the parallax:

| Layer | Movement | Source |
| --- | --- | --- |
| Environment plate | ~6px, pre-scaled 1.06 so shifting never exposes an edge | `hero-env.webp` (12 KB) |
| Ambient glow | ~20px | CSS radial-gradient, no asset |
| Contact shadow | ~14px | CSS radial-gradient, no asset |
| Vehicle | ~28px + `rotateY`/`rotateX` tilt, under `perspective: 1200px` | `hero-ev-car.webp` (80 KB) |

Driving layers through CSS variables rather than React state is deliberate: it lets the background live in `Hero.tsx` (server-rendered, no hydration flash) while still participating in the parallax. Idle motion is a slow sine so the hero is alive before any input; `prefers-reduced-motion` short-circuits the loop, the variables are never written, and every layer falls back to `0` — a completely static, correctly-composed hero.

**Vehicle:** `380×208` rendered, spanning 1%→32% of hero width with the wheel line 20% up from the hero's bottom, leaving **12px of clearance** above the Find Your Right EV panel (which overlaps the hero's bottom 52px). The copy column starts at 51%, so the vehicle geometrically cannot reach it.

**Environment plate** is generated, not painted: `scripts/generate-hero-environment.mjs` composes an atmospheric gradient, a two-band city silhouette with real atmospheric perspective, volumetric haze shafts, a horizon glow, a sparse perspective floor, a green light pool under the vehicle, and a right-side vignette that protects headline contrast. Authored at 2560×640 (4:1). **Re-run the script rather than editing the WebP by hand.**

### There is no Three.js here any more — and that history matters

This hero was **first built with Three.js / React Three Fiber** driving a real GLB, across several iterations, before the owner redirected to a 2.5D image approach. `HeroVehicle3D.tsx` and `HeroVehicle3DScene.tsx` are gone; the hero ships **0 canvases and no R3F import**. Remove with `npm uninstall three @react-three/fiber @react-three/drei` if the 3D route is abandoned for good.

If you *do* revisit 3D, the expensive lesson from that attempt: **an off-axis camera silently contributes its own rotation.** With the car at `x = −2.3` and the camera aimed at `x = −1.15`, the camera sat 28.1° off the car's nose; adding a 35° model yaw on top produced ~7° — a flat, head-on face that reads as the *rear* of the vehicle. The fix was to confine the canvas to the left 45% so the camera sits on-axis, at which point the model yaw *is* the viewing angle. Also: a camera stretched across the full 4:1 hero has a ~94° horizontal FOV and badly distorts anything off-centre.

### Four image-delivery traps, all hit and all verified live

These cost real time and are easy to re-introduce:

1. **`next/image` will destroy a transparent WebP.** It content-negotiates the output format and answered a request without an explicit `Accept: image/webp` by re-encoding to **JPEG** — which has no alpha channel, flattening the cut-out vehicle into a solid rectangle. `hero-ev-car.webp` therefore carries `unoptimized`. Do not remove it.
2. **`priority` preloads even when the container is `display:none`.** It emits a `<link rel=preload>` that fires regardless of CSS, so a `hidden lg:block` image still cost mobile its full weight.
3. **`<picture>` with a media-gated `<source>` does not survive hydration here.** It is the textbook answer and it failed: verified live at 1280px with `matchMedia('(min-width: 1024px)').matches === true` and correct markup, the element still resolved to the fallback, because React re-creates the `<img>` and locks in its `src` before the sibling `<source>` is consulted.
4. **What actually works: a CSS `background-image` on a `hidden lg:block` element.** A `display:none` element never fetches its background image. This is the gating mechanism for the environment plate and it is load-bearing — verified both ways: desktop fetches 12 KB verbatim, mobile fetches **zero bytes**.

The parallax rAF loop is gated on the same `(min-width: 1024px)` query, so mobile does not spin an animation loop writing variables nothing reads.

## ARCHITECTURAL DECISIONS

**Search architecture** — still client-side matching, but **no longer over the catalog** (rewritten 2026-08-16). The signature is now `searchVehicles(index, query, limit, scope)`: it takes a `SearchIndex | null` and imports no vehicle data at all. The index is a projection carrying only what a result needs to be matched, ranked, linked and thumbnailed (`VehicleIndexEntry` — no descriptions, variants, colours, specs or pricing), served from `/search-index.json` as a static ~22 KB file, fetched on first focus and memoized so several boxes share one request. `null` means "still loading" and the UI distinguishes that from "no matches".

Matching itself: tokenized multi-word scoring (every token must match, so extra words narrow), a Levenshtein fallback that compares individual words as well as whole names, `scope` filtering before scoring, and `CATEGORY_KEYWORDS` routing — with keywords suppressed for categories that have no vehicles, so "truck" doesn't advertise a route into an empty listing. Covered by `src/lib/search.test.ts`.

The old note here said `VehicleSearchBox` was "the place that would need to change if the catalog ever grows past trivial in-memory-scan size." That's now `search-index.ts` and the route handler instead — the UI is already decoupled from where results come from, and moving to a server-side search API would mean changing `loadSearchIndex()`, nothing in the component.

**Client bundle discipline** — added 2026-08-16, and the most easily-broken invariant in the codebase. **Never import `@/lib/data` (or anything that transitively reaches it) from a `"use client"` component.** The barrel builds a category→vehicles map in its module body, so importing *any* export from it pulls all 122 full records into that route's bundle; four client components were doing this for a brand colour alone, costing 110-130 KB per page. Client code imports `@/lib/data/oems`, `@/lib/data/categories`, `@/lib/vehicle-filter-options` and `@/lib/compare/slug` directly — all data-free by construction, and they must stay that way. Their server-side counterparts (`search-index.ts`, `compare/parse-slug.ts`, `filter-facets.ts`, `featured-vehicle.ts`) are Server-Component-only. When a client component genuinely needs vehicle records, hoist the lookup into its Server Component parent and pass the result as a prop — `FeaturedBanner`, `SearchCard` and `SectionCompareSimilar` are the reference examples. `/compare` is the one accepted exception. To check for regressions: `grep -o 'slug:"[a-z0-9-]*"' .next/static/chunks/*.js | sort -u | wc -l` should not report ~122 distinct slugs for any chunk outside the compare route.

**Data honesty as an architectural rule** — added 2026-08-16, previously an unwritten convention the Compare page followed and the VDP didn't. A specification is either real sourced data (`Vehicle.specs`, or a first-class `Vehicle` field) or it is `undefined` and renders through `components/common/UnavailableValue`. Nothing derives a spec from a formula. The subtlety worth internalising: `src/lib/compare/` reads `VehicleDetail`, so reintroducing a derived value in `toVehicleDetail.ts` silently changes comparison verdicts, winner crowns and schema.org markup — not just one page's copy. Calculators are the permitted exception and are distinguished by publishing their assumptions inline (running/charging cost print ₹/unit and km/day; `realWorldRange` carries its derating factors so the UI prints "Est. 80% of claim"). `src/lib/data/ev-motion/toVehicleDetail.test.ts` asserts the rule.

**Lead capture architecture** — added 2026-08-16, the project's only server-backed feature. `POST /api/leads` is the single entry point behind every CTA; the order is rate-limit → honeypot → validate → store, and nothing reaches the database before validation. `leadStore.ts` is the seam (same pattern as `vehicle-pricing/pricingSource.ts`), so swapping storage is a one-file change. Validation is shared with the dialog but the server copy is the real gate and is **allow-list based** — unknown `fields` keys are dropped rather than passed through, so a direct caller can't push arbitrary columns. Leads are never logged. `public.leads` runs RLS-deny-all with the app writing via a secret key that bypasses it; a publishable-key setup needs the separate INSERT-only policy migration and accepts that anyone holding the public key can bypass the route's guards entirely.

**Routing strategy** — flat URL shape: `/cars/[slug]`, `/two-wheelers/[slug]`, `/commercial/[slug]` (new), `/brands/[oem]`. Every place that builds a vehicle URL now goes through `routeSegmentFor(category)` (`src/lib/data/categories.ts`) instead of a hardcoded `category === "car" ? "/cars" : "/two-wheelers"` ternary — that pattern existed in at least 7 different files before this session (`search.ts`, `toVehicleDetail.ts`, `VehicleCard.tsx`, `CompareTable.tsx`, `ListingCard.tsx`, `TrendingCompactCard.tsx`, `SectionSimilarElectricCars.tsx`) and was a real source of "forgot to add the third branch" risk when commercial was introduced; it's now one function. All dynamic segments use `generateStaticParams` except the four pages that read `searchParams`.

**Component hierarchy** — same three parallel "vertical slices" as before (`components/home/*`, `components/vehicle-detail/*`, `components/vehicles/*`), all now on one design-token system. Two new shared primitives sit alongside them rather than inside any one slice: `LocationSelector` (`components/layout/`) and `ResponsivePopover` (`components/common/`) — both reusable independent of category.

**Shared utilities** (`src/lib/`) — `categories.ts` is the newest and most load-bearing one: it's the single source of truth for "which categories exist," and every other generalization in this session (`derive.ts`'s builders, brand pages, sitemap, compare tabs, filter config lookup) is downstream of it. `vehicle-filter-options.ts` now holds per-category `CategoryFilterConfig` objects (bounds + sub-type facet) instead of each listing page defining its own. `listing-params.ts` gained `buildListingSearchParams` (the inverse of `parseListingParams`) so the homepage's filter chips and the listing page's own sidebar can't encode filter state two different ways. Treat any new "same logic in two/three places" the same way — generalize through the registry, don't add a fourth copy.

**Data flow** — `src/lib/data/{cars,two-wheelers,commercial,oems}.ts` (raw records) → `src/lib/data/index.ts`'s `getVehiclesByCategory` (a `Record<VehicleCategory, Vehicle[]>` lookup, not a ternary) → `src/lib/data/ev-motion/{content,derive,toVehicleDetail}.ts` (adapters, now category-parameterized) → components. Nothing fetches at runtime. If you need a new derived view, add a function to `derive.ts` parameterized by category rather than a new per-category const.

**State management** — still no global state library, with one genuine exception added this session: `LocationContext` (`src/context/`) is the first real cross-component global state the app has needed, because 3+ unrelated components (Navbar, SearchCard, SponsoredBanner) must reflect one selected-city value. It's a plain React Context + `useState`, persisted to `localStorage`, hydrated client-side after mount (server default is "Delhi" to avoid a hydration mismatch — the same pattern the Navbar's pre-existing dark-mode toggle already used). Everything else (listing filters, compare-page selection, dialog open-state) remains local `useState`, optionally URL-synced.

**Responsive strategy** — Tailwind's `sm`/`lg`/`xl` breakpoints, plus scoped custom tiers added only where a genuine overflow bug demanded one. The rule holds: prefer `min-w-0` + flexible sizing + responsive visibility over fixed pixel widths, and verify live at the exact pixel width where a bug is suspected, not just round breakpoint numbers. **A specific gotcha found by the production polish pass, worth generalizing**: any CSS Grid container that has a `.scroll-row` (horizontal-scroll) descendant needs its fractional track written as `minmax(0, 1fr)`, never a bare `1fr` — a bare `1fr` track's implicit min-width is the track's *max-content* size, so a horizontal-scroll row's full unscrolled width silently stretches the whole grid (and therefore the whole page) instead of being clipped by `overflow-x-auto` the way it visually appears to be. `overflow: auto` does not opt an element out of contributing to an ancestor's intrinsic-sizing calculation on its own — the ancestor track needs `minmax(0, …)` (or the child needs `min-width: 0`) as well. This is exactly the same underlying class of bug as the original QA cycle's 1280px Navbar overflow, just one layer up the tree (grid track sizing instead of flex-item sizing) — if a new horizontal-scroll section is ever added inside a grid, check this first.

**Currency formatting** — `src/lib/utils.ts`'s `formatPriceLakh(lakh)` / `formatPriceRangeLakh(low, high, separator?)` are now the single source of truth for rendering a `priceRangeLakh` value as a `₹` string, switching to crore notation (`₹7.50Cr`) at/above ₹100L so the site doesn't read oddly for the Batch-2-added luxury cars. Every prior ad-hoc `` `₹${x.toFixed(2)}L` `` inline template (4 call sites: `VehicleCard.tsx`, `CompareTable.tsx`, `derive.ts`, `SponsoredBanner.tsx`) was replaced with a call to these. **Don't hand-roll price formatting again** — call the shared helper.

**Location-aware pricing** — `src/lib/data/state-charges.ts` is a new, small, honestly-labeled-as-estimated table (`STATE_CHARGES: Record<string, StateCharges>`, keyed by the same state-name strings `cities.ts` uses) modelling the real-world pattern that many Indian states fully or partially waive EV road tax and some layer an additional purchase subsidy on top. `chargesForState(state)`, `subsidyMessageForState(state, category)`, and `subsidyRowsForState(state, category)` are the three functions every price/subsidy-displaying component should call rather than hardcoding a flat percentage or a category-only (non-state-aware) message — see `SidebarPriceSummary.tsx`, `SectionCompareSimilar.tsx`, `SubsidyCalculatorCard.tsx`, and `SectionOwnershipTools.tsx` for the pattern.

(c) A figure that **reconciles across units** (110 kW = 147.51 bhp = 149.55 PS) is trustworthy; one that doesn't is a guess wearing precision, and belongs omitted.
